Life

1 The loop in three moves

Everything in Life/ exists to support this cycle.

  • /morning — today's calendar blocks and each one's minimum. Doesn't replan unless something actually changed.
  • Work the blocks. Each carries a concrete minimum. Empty windows stay empty on purpose — not a gap to fill with busywork.
  • /evening — an honest minimum-done verdict, tomorrow's plan in ~10 minutes, one factual entry appended to Patterns/observation-log.md.

/weekly, once a week: a short retrospective on the last seven days, then an interview about the week ahead — before anything gets scheduled.

No fifth stop on this circle for capture — dropping a task or an idea happens continuously, any time, not on a schedule. Where each thing actually goes: §2, right below.

3 The three commands

What it doesWhen
/morningShows today's blocks + minimums, sets the toneStart of the day
/eveningCloses the day, plans tomorrow, writes one Patterns entryThe keystone habit — end of every day, ~10 min
/weeklyRetrospective + an interview about next week, then blocking timeOnce a week

Then /roadmap. It reads your avatar and offers 2–3 genuinely different roadmaps (what wins when things collide, the phases for the next ~3 months, the weekly hours) with a recommendation; you pick one, and it writes roadmap-brief.md section by section, showing each change first. Phases have a checkable definition of done and a date; priorities are one strict order, with protected time (sleep, family…) kept outside it; the Now section holds the current step and the weekly targets, which /weekly proposes to update each week. Run /roadmap again when a phase ends: it checks the definition of done criterion by criterion, goes through the backlog and opens the next phase. Refuses to run while John's sample data is still in the vault (offers to clear it).

Once, before the first /morning: /avatar. A 20–25 minute interview — who you are, where you're heading, what you can do (skills, with evidence), your limits, how you actually work. It writes Life/roadmap/avatar.md, which the three commands and the Library read instead of guessing. On the first run it also offers to clear the sample person's (John's) data — to the system trash, nothing permanent, asked separately for Life and Library. It asks only what would change your priorities: relationships, family, health and exact money stay out unless you bring them up, and any question can be skipped. Run it again to update; it only walks the sections that changed.

All three follow the same rule during planning: you get options with a stated recommendation, not a silently-built plan and not an open "what do you want to do?" The decision of what's possible is the agent's; the choice of what actually happens is yours.

9 What NOT to do

  • Don't expect an empty calendar window to get filled with busywork — empty is deliberate.
  • Don't ask for a whole week planned silently. Day/week planning is always options with a stated recommendation; you choose.
  • Don't treat a declared time estimate as accurate by default — it gets compared against what actually happened.
  • Don't fill in your own habit checklist for the agent, or expect the agent to fill it for you — that tracker has to measure you, not the agent's judgment of you.
  • Don't touch Notes/, journaling sections, or roadmap-brief.md expecting the other side to follow along silently — sacred runs both ways.
  • Don't call something a confirmed pattern after it happened once — the threshold is 3, and it's hard.
  • Don't start a new project because it seems useful. An idea goes to backlog.md, not into the current block.
  • Don't ask the agent to count a definition of done as met because it's "mostly there". The verdict follows the facts you give; a new fact changes it, pushing doesn't.
  • Don't git add -f your avatar, journal or notes into a public repo — they're ignored on purpose (see Vault-wide).
Life

1 The idea: one place, run by an agent

Most productivity setups make you the maintainer: you build the databases and templates in Notion or a dozen apps, keep them tidy, remember to review them, and decide every day what to do next. The system becomes one more project, and it gets dropped like the others. This vault starts from the opposite end: one place for the running of your life, and an agent that does the running. You don't design a system. You're interviewed once about who you are and where you're heading, and from then on the agent plans from what it knows, keeps the calendar, inbox and journal in order, triages, writes the factual record, compiles what you learn, and tells you what's due and what's slipping. You do the living: show up, report honestly, choose between the options it offers, write your own journal.

"Your whole life" means four things in one folder of plain markdown, no app-to-app glue: what you're doing (calendar blocks with minimums, an inbox), where you're heading (avatar and roadmap), how it's going (journal and patterns), what you know (the Library). It doesn't replace specialised tools like your bank or medical records — it's where you decide and track what you do with your time and goals.

Projects get dropped. Not from lack of ideas — from the accumulation of small, unglamorous bookkeeping: what was the plan again, did yesterday actually go the way it felt like it went, is this really a pattern or just one bad day dressed up as insight. This vault exists to carry that bookkeeping so the load on you doesn't compound. It has to work, not become another project that gets dropped.

2 The mechanism, in five sentences

Every block on the calendar carries a minimum — a concrete, checkable thing, not a vague intention. /evening renders an honest verdict on whether that minimum actually happened, and that verdict is the agent's call, not a self-grade. A single good or bad day never gets to redefine what's true about you — an observation only becomes a pattern after showing up three separate times in the raw log. A written roadmap-brief settles priority order once, so it isn't re-litigated from scratch every time two things collide. None of this replaces your judgment — it just stops the same small decisions from having to be remade, exhausted, every single day.

4 Your role and the agent's

You: show up to the blocks, report what actually happened, honestly. Choose between the options offered during planning — the choice is always yours. Push back when a verdict feels wrong, with a fact the agent didn't already have — not just by disagreeing.

The agent: proposes options with a stated recommendation, never a silently pre-built plan. States the declared minimum before judging whether it was met. Keeps the honest-verdict call itself — a string of small wins on a day one priority got skipped is exactly the read that lets projects slide, so it doesn't hand that judgment back to you to grade yourself. Writes to Patterns/ twice a day (open and close), and only promotes an observation to a confirmed pattern on the third repeat, never the first.

5 What's sacred, and why

Notes/, the journaling sections in Journal/, filled-in frontmatter values, avatar.md and roadmap-brief.md are never rewritten without an explicit instruction — /avatar and /roadmap write them by design, and /weekly may change section 6 of the brief, only after you confirm. Self-tracking data and personal reflection lose their entire point the moment someone else can quietly edit them — a habit streak the agent could pad isn't a real streak, and a journal entry it could clean up isn't an honest one.

6 How this connects to Library

The bridge runs one way: /morning, /evening, and /weekly may drop a file into Library/sources/inbox/ and touch nothing else in Library. That's deliberate — compiling a source mid-block turns a ten-minute check-in into a forty-minute detour. The Library pipeline reads roadmap-brief.md and avatar.md for context but never writes back into Life/. Two different jobs, kept from bleeding into each other.

Library

Three files remain separate from this page: SCHEMA.md (rules, for the agent — skip it), CAPTURE.md (full Clipper/config setup), INDEX.md (the catalog of every page, mostly read by the agent). What used to be CHEATSHEET.md and IDEA.md now lives here, as this page's Library tab.

1 The whole Library is three actions

Dropping is free and automatic. Click and go back to what you were doing. Nothing to describe, tag, or think about.

Compiling does NOT happen by itself. Ever. You trigger it consciously, when you have 20–40 minutes for it — letting other people's web pages into the base without looking is an open door for prompt injection.

Asking is the reward for the other two. That's when the base gives back what you put into it.

Setting up the Web Clipper (browser extension)

The main way anything from the web — an article, a video transcript, a docs page, a thread — gets into Library/sources/inbox/. It's a browser extension, installed separately from anything install-plugins.py touches (that script only manages Obsidian plugins, not your browser).

  1. Install the official Obsidian Web Clipper extension (search your browser's extension store — Chrome, Firefox, and Chromium-based browsers are all supported).
  2. In the extension's settings, pick this vault, then set note location to Library/sources/inbox. This is the one step that actually matters — by default the extension targets a generic clippings folder that nothing here ever compiles.
  3. Don't touch the clip template, don't tag or describe anything while clipping — a clip should be one click, nothing else.

It works on the page as already rendered, so it also handles SPAs, JS, and a full YouTube transcript with timestamps — no separate download tool needed. If a page won't clip (paywall, a broken SPA), that's the extension's own limitation — paste the text with /source instead.

4 Running an ingest, step by step

Ingest is always manual, always one file at a time — there's no automatic trigger on a hook.

  • Check what's waiting: ls Library/sources/inbox/.
  • Ask the agent to run /library (or say "ingest the next file in the queue").
  • The agent reads the source, decides what's a real mechanism worth its own wiki page versus what's just a pointer, writes or updates pages, wires new ones into their folder's MOC, updates INDEX.md and log.md, then moves the source out of inbox/ into the matching archive folder — never edits its content.
  • Run the linter: python3 Library/lint.py (Windows: py Library/lint.py). Exit code 1 means something needs fixing. --fix auto-corrects staleness flags; everything else you fix by hand.

A big queue with nothing getting ingested is itself useful information — it usually means there isn't currently time for this part of the loop, and that's fine to leave as-is rather than rush.

Library

1 The problem this solves

The Library is the what you know part of the one place this vault is meant to be — so what you learn doesn't live in a different app from what you plan.

You learn something while working. You understand it. A month later it's nowhere — it stayed in a chat with an LLM, in a browser tab, or in a transcript you'll never revisit.

The standard fix is RAG: dump files in, and the model re-searches them from scratch on every question. The problem: nothing accumulates. Ask the same question again in a month and the model digs through the same files from zero, again.

2 Karpathy's idea, in five sentences

Instead of searching raw files on every question, compile them once into a set of linked markdown pages and then maintain them. The cross-links already exist. Contradictions are already flagged. The next source doesn't land beside what's there — it gets woven into it.

The point worth remembering: the tedious part of a knowledge base isn't reading or thinking, it's the bookkeeping — and that cost is exactly what an LLM doesn't get tired of paying. That's the same abandonment pattern the whole vault exists to fight — just moved onto a wiki.

3 Three layers, nothing more

LayerHereWho writes
Raw sourcesLibrary/sources/ + Life/Notes/, books/You. The agent reads, never changes
WikiLibrary/wiki/The agent. You read and judge
SchemaLibrary/SCHEMA.mdTogether, deliberately

Three operations: ingest (drop a source, it gets broken down and woven in), query (ask, get a cited answer from the wiki), lint (a script checks health). Two navigation files: INDEX.md and log.md. That's the whole implementation — zero lines of code.

4 An early decision that got reversed

An earlier version decided pages should be immutable — never rewrite one, always create a new one with a supersedes/refines relation. The trigger question: "what if the sources overlap — don't things end up duplicated?"

With immutable pages — yes, unavoidably. A second source about the same tool has to make a second page about the same thing. Cleanup needs version chains and a consolidation command — exactly the machinery an earlier plan already predicted.

With mutable pages, the problem doesn't arise. A second source lands on the existing page, source-count goes 1→2. Overlap stops being a threat and becomes a signal: "confirmed twice, not just claimed once." What protects you instead: git. wiki/ is in the repo — every write is reversible with git checkout, on the one hard condition that there's a commit after every ingest. The system got smaller, not bigger.

5 What happens on "ingest" — one real example

  • The source lands untouched in sources/, exactly as it arrived.
  • It gets read and candidates get listed. Every candidate needs a quote from the source — no quote, it's out. The guard against inventing things the material never said.
  • Pages get written. A topic folder appears in wiki/, each page answering exactly one question.
  • It gets woven into what's already there. An existing note on the same subject gets a refines: field pointing at it — your note stays untouched, new pages hang underneath.
  • INDEX.md and log.md get an entry, so it can be found and dated.
  • Lint runs — every page needs a source, dead links and orphans get flagged.

6 How this sits on top of the rest of the vault

The vault holds real quantities of knowledge that live nowhere compiled: full chat checkpoints, programming notes, reading conclusions, course material. None of it needs to move or get deleted. Those files stay exactly where they are — that's the source layer. The agent only reads them and builds pages alongside them in wiki/.

What the agent never touches: Life/Journal/, Life/Calendar/, Life/Patterns/, Life/roadmap/. That's the day-to-day operating system, not knowledge.

7 Your role and the agent's

You: choose what goes in. Judge whether a page captures why you saved the source. Say "too shallow" or "too much." Ask questions.

The agent: reads, breaks down, writes pages, maintains cross-links, keeps the index and the chronicle, runs lint. Never changes your notes, deletes sources, writes to Life/Journal/ or Life/Calendar/, or compiles without your command.

Vault-wide, not zone-specific

A few things that don't belong to Life or Library specifically.

The Overview banner picture (Life OS Hub)

The Overview tab can show an image behind the header. The repo ships without one, since it would have to be generic or someone else's art. Two ways to set it:

  • Drag a picture straight onto the empty banner. Life OS Hub saves it, names it and shows it immediately — nothing to configure. Drag another one onto it later and it replaces the old one the same way: the current pictures live in System/Attachments/banners/, and a replaced one isn't deleted but moves to System/Attachments/old-banners/ as dark mode 1, dark mode 2, … (an identical picture is never archived twice). Everything in System/Attachments/ is git-ignored.
  • Or drop the file anywhere in the vault with "dark mode" or "light mode" somewhere in the filename — gif, png, jpg, webp or avif, any dimensions. Life OS Hub finds it within a second, no restart; the newest matching file wins.

Crop position is tunable per mode in Style Settings → Life OS Hub → banner, for when your picture's focal point isn't centred.

The Colors tab, in full (Life OS Hub)

Background at the top sets what's behind everything, separately for dark and light mode: Solid, or Gradient (two to four colours, drag the angle, Reverse flips the order), with a live preview. Glows add soft spots of colour on top (position, size, strength); the Aurora preset loads the theme's own look so you can tweak it. Theme brings back the theme's own gradient.

Below it, click a swatch to copy its hex. Under From your banner, Use as accent sets the accent from that colour. To change a colour by hand, use the picker or type a hex; Reset returns it to the Style Settings (or theme) value. Colours changed here override Style Settings and show an overridden badge. Theme colours (Obsidian's own) are view-only until you tick Advanced, where Reset all clears every theme override.

A contrast warning appears when text or accent drops below 4.5:1 against the background; nothing is changed automatically.

The sample person (John): clear him, bring him back

A fresh vault ships with a made-up person's data — John's calendar, journal, notes, roadmap brief and a small wiki — so the Hub shows something on first open. /avatar offers to clear it on the first run, and /roadmap refuses to write next to it. You can also run the script yourself; every command is a dry run until you add --apply:

# Windows: py instead of python3
python3 System/demo/demo.py clear                          # dry run: prints the plan
python3 System/demo/demo.py clear --apply                  # John's files go to the system trash
python3 System/demo/demo.py clear --apply --keep-library   # clear Life/, keep the sample Library
python3 System/demo/demo.py restore                        # dry run: what of John is missing
python3 System/demo/demo.py restore --apply                # write back only what is missing

Clear touches only files that are still John's: anything you changed is left alone and reported, so your own journal entries survive. Nothing is deleted for good — the files sit in the system trash. Empty placeholders replace INBOX, the brief and the Patterns files, so the plugins and commands keep finding them. Restore only adds what's missing (delete one John file and only that one returns), never overwrites, matches the dates to what's already there, and refuses while avatar.md exists — --mix overrides that. --replace-stubs swaps an empty placeholder for John's version. The marker System/demo/.demo-active lists which parts (life, library) are still in the vault.

Privacy: what git ignores on purpose

avatar.md, the roadmap brief (and its .previous copy), backlog.md, INBOX.md, Journal/, Notes/, the two Patterns/ files and everything in System/Attachments/ (photos and images you paste into notes, the Hub's banner pictures) are in .gitignore. They're the most personal things in the vault, and a fork pushed to a public repo would otherwise publish them. Only System/Attachments/.gitkeep stays tracked, so the folder exists on a fresh clone. The template ships John's versions already tracked; after you clear him, git drops what is left of them from its index (the files stay on disk). If you want one in a private repo: git add -f <file>. The trade-off is real: git no longer backs these files up for you.

Opening .html files in a real browser

Obsidian's HTML Reader plugin sandboxes every .html file it opens — it forces every link inside one into a new tab that its own sandboxed view then ignores, so nothing in this page, START-HERE.html, or any other .html you drop into the vault actually clicks. No click, Ctrl+click, or Cmd+click gets through, and there's no fix on the page side that doesn't mean running arbitrary JavaScript on every .html file in the vault by default — not something worth trading away for link-clicking.

Instead: Cmd/Ctrl+Shift+B opens the active .html file in your real default browser, where every link works normally. It's a small QuickAdd macro (System/scripts/quickadd-open-in-browser.js, choice "🌐 Open in browser"), not a native Obsidian feature — Obsidian's own built-in Open in default app command exists too, but only fires when the file is already the active pane, so it couldn't be triggered from anywhere. This one can: press it from any tab, on any .html file, and it opens that file; press it with nothing .html active and it opens HANDBOOK.html instead of doing nothing.

Ships pre-configured — no browser path to set, no per-user setup, works on Windows and macOS alike (Mod resolves to Ctrl or ⌘). If it stops responding after editing the macro's script, QuickAdd needs a reload to pick it up: disable and re-enable the plugin, or restart Obsidian.

Undoing changes with git

This vault is version-controlled — git is your only safety net, since nothing here syncs automatically between devices.

git log --oneline -20                       # recent restore points
git log --oneline -- "Life/INBOX.md"         # history of one file
git restore "Life/INBOX.md"    # discard uncommitted changes to one file
git restore .                  # discard ALL uncommitted changes — no undo after this
git show <commit>:"Life/INBOX.md"                    # preview an old version, prints to terminal
git restore --source=<commit> "Life/INBOX.md"         # restore just that one file from an old commit

Always preview with git show before restoring — it's the only one of these that can't hurt anything. Commit as often as you can stand to: nothing you haven't committed can be recovered if you overwrite it later.
